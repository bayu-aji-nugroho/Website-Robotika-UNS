Spesifikasi Backend: Data Registrasi Calon Anggota

Panduan implementasi API intake form pendaftaran dan persistensi database

Versi Dokumen: 1.0.0
Target Rilis: OPREC 2026
Sifat: Teknis / Agnostik Database

1. Ruang Lingkup dan Batasan Sistem

Dokumen ini menjadi standar integrasi antara antarmuka formulir pendaftaran (frontend web) dengan service backend. Fokus dokumen ini mencakup siklus penerimaan data awal, yaitu:

  • Penerimaan data formulir dari antarmuka web ke endpoint API backend.
  • Validasi identitas mahasiswa, integritas pilihan divisi, serta validasi berkas fisik CV.
  • Penyimpanan berkas fisik CV ke storage (object storage atau local disk server).
  • Penyimpanan data pendaftar ke tabel database relasional.
  • Pengembalian status response HTTP beserta kode pendaftaran unik ke frontend.

Alur seleksi lanjutan seperti tahapan review admin, wawancara, dan pengumuman kelulusan tidak dibahas pada dokumen ini dan ditangani terpisah setelah data tersimpan.

2. Alur Pengiriman Data (End-to-End Workflow)

  1. Pengisian Form di Frontend: Calon anggota menyetujui syarat, mengisi identitas diri (Nama, NIM, Prodi, Angkatan, WhatsApp), memilih 2 divisi beserta alasan, mengunggah berkas CV format PDF (maksimal 1.0 MB), dan mencentang keabsahan berkas.
  2. Validasi Client-Side: Frontend memeriksa kelengkapan data, memvalidasi format berkas PDF, serta menghasilkan kode registrasi lokal dengan format ROB-UNS-2026-XXXX.
  3. Pengiriman HTTP Request: Frontend mengirim request ke backend. Metode default yang digunakan adalah multipart/form-data karena membawa berkas fisik secara langsung.
  4. Pemrosesan di Backend:
    • Validasi keberadaan field wajib dan keabsahan tipe berkas (MIME application/pdf, batas ukuran 1 MB).
    • Pemeriksaan duplikasi NIM pada database agar satu mahasiswa tidak mendaftar dua kali.
    • Penyimpanan berkas CV ke storage engine dan pembuatan path penyimpanan.
    • Penyimpanan baris data pendaftar ke tabel database.
  5. Respons HTTP: Backend mengembalikan kode HTTP 201 Created disertai payload konfirmasi. Frontend menampilkan halaman tanda terima dan tautan grup WhatsApp.

3. Spesifikasi Endpoint API

POST /api/v1/registrations

Menerima berkas fisik CV beserta seluruh data formulir pendaftaran calon anggota.

Content-Type yang Diterima: multipart/form-data (disarankan) atau application/json (bila file diunggah terpisah via presigned URL).

Daftar Field Multipart (Form-Data Contract)

Field Key Tipe Data Status Ketentuan & Validasi Contoh Nilai

nim String Wajib Nomor Induk Mahasiswa, huruf kapital, unik, maks. 30 karakter. I0724018

5. Aturan Validasi Sisi Backend (Server Validation)

Backend wajib mengeksekusi validasi server-side berikut sebelum melakukan penulisan ke database:

Area Validasi Ketentuan Pengecekan Respons Jika Gagal
Keunikan NIM Query database untuk memastikan NIM belum pernah terdaftar sebelumnya. HTTP 409 Conflict: NIM sudah terdaftar dalam sistem
Kombinasi Divisi primary_division_id tidak boleh sama dengan secondary_division_id. Kategori harus bernilai teknis atau non-teknis. HTTP 400 Bad Request: Pilihan divisi 1 dan 2 tidak boleh sama
Validasi Berkas CV 1. Ukuran file tidak boleh melebihi 1.048.576 bytes (1.0 MB).
2. MIME type harus application/pdf.
3. Magic byte header file harus diawali string %PDF- (hex: 25 50 44 46). 		HTTP 400 Bad Request / 413 Payload Too Large: Berkas harus berformat PDF dan maksimal 1 MB
Sanitasi Kontak WhatsApp Pastikan nomor hanya berisi karakter angka. Konversi awalan internasional +62 atau 62 menjadi format lokal 08. Sanitasi otomatis di server atau tolak jika panjang nomor kurang dari 10 digit.
Persetujuan Syarat Nilai agreed_requirements dan agreed_truth harus bernilai true. HTTP 400 Bad Request: Persetujuan syarat dan keabsahan berkas wajib disetujui

6. Desain Skema Database Relasional (SQL DDL Standar)

Skema database berikut menggunakan sintaks ANSI SQL standar yang kompatibel dengan PostgreSQL, MySQL, MariaDB, SQLite, maupun BaaS (Supabase): 

-- Tabel utama untuk menyimpan pendaftaran anggota baru
CREATE TABLE registrations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  registration_code VARCHAR(32) NOT NULL UNIQUE,
  full_name VARCHAR(255) NOT NULL,
  nim VARCHAR(30) NOT NULL UNIQUE,
  prodi VARCHAR(150) NOT NULL,
  angkatan VARCHAR(10) NOT NULL,
  whatsapp VARCHAR(30) NOT NULL,
  
  -- Pilihan Divisi Pertama
  primary_division_id VARCHAR(100) NOT NULL,
  primary_division_name VARCHAR(150) NOT NULL,
  primary_division_category VARCHAR(20) NOT NULL,
  primary_reason TEXT NOT NULL,
  
  -- Pilihan Divisi Kedua
  secondary_division_id VARCHAR(100) NOT NULL,
  secondary_division_name VARCHAR(150) NOT NULL,
  secondary_division_category VARCHAR(20) NOT NULL,
  secondary_reason TEXT NOT NULL,
  
  -- Berkas CV dan Penyimpanan
  cv_file_name VARCHAR(255) NOT NULL,
  cv_file_size_bytes BIGINT NOT NULL,
  cv_storage_path TEXT NULL,
  cv_file_url TEXT NULL,
  
  -- Persetujuan dan Waktu
  agreed_requirements BOOLEAN DEFAULT TRUE NOT NULL,
  agreed_truth BOOLEAN DEFAULT TRUE NOT NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL
);

-- Indeks performa untuk pencarian identitas dan verifikasi
CREATE UNIQUE INDEX idx_registrations_nim ON registrations(nim);
CREATE UNIQUE INDEX idx_registrations_code ON registrations(registration_code);
CREATE INDEX idx_registrations_created_at ON registrations(created_at);
Catatan Portabilitas SQL: Bila database target adalah MySQL atau MariaDB, ganti tipe data UUID DEFAULT gen_random_uuid() menjadi VARCHAR(36) atau kolom id BIGINT AUTO_INCREMENT PRIMARY KEY, dan sesuaikan TIMESTAMP WITH TIME ZONE menjadi DATETIME DEFAULT CURRENT_TIMESTAMP.

7. Manajemen Penyimpanan Berkas CV (Storage Strategy)

Berkas CV disimpan pada storage engine yang terpisah dari tabel database. Kolom database hanya menyimpan referensi path atau public/signed URL.

  • Struktur Folder: Gunakan partisi tahun angkatan: cv-uploads/[angkatan]/[NIM]_[clean_filename].pdf.
  • Sanitasi Nama File: Hapus spasi dan karakter khusus dari nama asli berkas untuk mencegah masalah encoding dan path traversal: Contoh: cv-uploads/2025/I0724018_Dimas_Arya_Prasetya_CV.pdf.
  • Opsi Backend Storage:
    1. Object Storage (S3 / MinIO / GCS / Supabase Storage): Simpan path relatif di kolom cv_storage_path dan URL akses di cv_file_url.
    2. Local Disk Server: Simpan berkas di direktori aman server (misalnya /var/storage/cv/...) yang dilayani melalui reverse proxy Nginx terotorisasi.

8. Standar Kode Respons HTTP dan Format Respons

Status Kondisi Format Payload JSON yang Diharapkan
201 Created Data formulir dan berkas berhasil divalidasi dan disimpan. 
{"success": true, "message": "Pendaftaran berhasil disimpan", "registrationCode": "ROB-UNS-2026-1042"}
400 Bad Request Field wajib kosong, format keliru, atau berkas bukan PDF. 
{"success": false, "message": "Validasi gagal", "error": "Pilihan divisi pertama dan kedua tidak boleh sama"}
409 Conflict NIM mahasiswa sudah pernah terdaftar di database. 
{"success": false, "message": "Data sudah terdaftar", "error": "NIM I0724018 sudah pernah didaftarkan sebelumnya"}
413 Too Large Ukuran berkas CV melebihi batas 1.0 MB. 
{"success": false, "message": "Berkas terlalu besar", "error": "Ukuran berkas CV maksimal adalah 1.0 MB"}
500 Error Gangguan koneksi database atau kegagalan penulisan storage. 
{"success": false, "message": "Terjadi kesalahan internal server", "error": "Gagal menyimpan data pendaftaran"}

10. Checklist Implementasi Developer Backend

  • Tabel registrations telah dibuat lengkap dengan constraint unik pada kolom nim dan registration_code.
  • Konfigurasi upload parser server (seperti multer di Node.js, request files di Python, atau FormRequest di Laravel) membatasi ukuran request maksimal 2 MB (1 MB untuk CV ditambah buffer field teks).
  • Pengecekan MIME type berkas dilakukan di sisi server, bukan hanya membaca ekstensi nama file.
  • Penyimpanan berkas ke folder/bucket menghasilkan URL yang dapat diakses oleh panitia seleksi.
  • Format respons JSON konsisten dengan properti success, message, dan registrationCode saat sukses.
  • Handling error duplikasi NIM mengembalikan status HTTP 409 dengan pesan yang ramah kepada pengguna.
